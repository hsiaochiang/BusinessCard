# 名片管理系統（Android APK + Google 試算表）— 初版需求說明（Specify 草稿）

> 說明：本文件聚焦在「名片掃描結果，可在電腦上方便編輯、查詢」的需求設計，資料唯一來源為 Google 試算表。未包含完整 UI 設計與 API 細節，可作為後續輸入 SpecKit / Codex 的基礎說明。

---

## 1. 系統概要

### 1.1 系統目標

- 建立一套以 **Android APK + Google 試算表** 為主的名片管理系統。
- 名片可由手機端（拍照 + OCR）建立與修改，並同步到 Google 試算表。
- 電腦端使用者可直接在 Google 試算表中編輯、查詢、篩選名片資料，不需另裝客戶端軟體。
- Google 試算表為「**唯一真實來源（Single Source of Truth）**」，Android App 僅為操作介面。

### 1.2 使用情境概述

1. 使用者在 Android 手機上安裝名片管理 App。
2. 使用者以手機拍攝紙本名片，App 進行 OCR 辨識，產生名片欄位。
3. 使用者確認／修正欄位後儲存，App 透過 Google Sheets API 將資料寫入指定試算表。
4. 使用者在電腦上開啟 Google 試算表，直接編輯名片資料（如補充備註、調整標籤）。
5. 手機端再次開啟 App 查詢時，讀取的即為最新的試算表資料。

---

## 2. 資料儲存與架構設計

### 2.1 主資料庫：Google 試算表

- 使用 Google 試算表作為名片資料的主儲存介面。
- 試算表檔案範例名稱：`BusinessContacts`。
- 主要工作表名稱：`Contacts`。
- 所有名片資料都以「一列一筆」方式儲存於 `Contacts` 工作表。

### 2.2 欄位設計（Contacts 工作表）

`Contacts` 工作表欄位建議如下：

| 欄位名稱       | 資料型態 | 必填 | 說明 |
|----------------|----------|------|------|
| id             | 文字     | Y    | 系統唯一識別碼（UUID 或流水號），由系統產生，避免重複。 |
| name           | 文字     | Y    | 姓名。 |
| company        | 文字     | N    | 公司名稱。 |
| title          | 文字     | N    | 職稱。 |
| mobile         | 文字     | N    | 手機號碼。可包含國碼、`+`、`-`、空格。 |
| phone          | 文字     | N    | 市話或公司電話，視需要可含分機。 |
| email          | 文字     | N    | 電子郵件地址。 |
| address        | 文字     | N    | 通訊地址或公司地址。 |
| tags           | 文字     | N    | 標籤，多個標籤以逗號分隔，如：`電商,物流,既有客戶`。 |
| note           | 文字     | N    | 備註，例如認識場合、會議重點、客戶偏好等。 |
| source         | 文字     | N    | 資料來源，範例值：`scan`（掃描）、`manual`（手動輸入）、`import`（匯入）。 |
| image_url      | 文字     | N    | 名片影像於 Google Drive 的檔案連結。 |
| created_at     | 日期/時間 | Y   | 建立時間，建議格式 `YYYY-MM-DD HH:MM`。 |
| updated_at     | 日期/時間 | Y   | 最後更新時間，任何欄位變更時需更新。 |
| last_contact_at| 日期      | N   | 最近一次與該聯絡人互動日期（電話、會議、簡報等）。 |

> 備註：實作上可根據 Google Sheets 支援型態，將時間欄位儲存為文字或日期時間欄位，但格式需保持一致。

### 2.3 欄位保護與驗證規則

- `id` 欄位：
  - 由系統產生，不建議人工修改。
  - 建議設定為「受保護範圍」，一般使用者不應直接變更。
- `email` 欄位：
  - 建立資料驗證規則，限定符合 Email 格式。
- `mobile`、`phone` 欄位：
  - 建議設定為允許數字、空白、`+`、`-` 的組合，以降低輸入錯誤。

## 3. 桌面端（Google 試算表）編輯與查詢需求

### 3.1 編輯需求

1. 使用者可直接在 `Contacts` 工作表中：
   - 新增一列名片資料。
   - 修改任何非保護欄位（如姓名、公司、標籤、備註等）。
   - 進行複製／貼上、批次更新等操作。
2. 系統（或後續自動化腳本）應確保：
   - 每一筆新資料必須有唯一 `id`。
   - 新增或修改時，自動（或半自動）填寫／更新 `created_at` 與 `updated_at` 欄位。
3. 編輯輔助設計：
   - 固定第一列表頭（Freeze Row 1），讓欄位名稱在捲動時仍可見。
   - 可預先定義常用標籤清單（選擇性，可另建 `Tags` 工作表做說明）。

### 3.2 查詢與篩選需求

1. 使用者可以透過 Google 試算表內建功能進行：
   - 關鍵字搜尋（姓名、公司、email、標籤、備註等）。
   - 篩選與排序（例如依公司排序、依建立日期排序）。
2. 建議預先建立數個「篩選視圖」供日常使用，例如：
   - 視圖 A：依 `name` 升冪排序，顯示全部欄位。
   - 視圖 B：篩選 `tags` 欄位中包含「既有客戶」關鍵字的名片。
   - 視圖 C：`created_at` 在最近 30 天內（新增的名片）。
   - 視圖 D：`last_contact_at` 超過 180 天（需回訪的客戶）。
3. 若後續需求提升，可在試算表上方加入範本列（如常用條件），或改由 Web 後台提供更友善的查詢介面（預留未來擴充）。

## 4. Android App 與 Google 試算表整合需求

### 4.1 連線與認證

1. App 必須能與 Google 帳號進行 OAuth 認證，取得存取指定試算表的權限。
2. 使用者首次啟動 App 時：
   - 需選擇使用的 Google 帳號。
   - 需選擇或建立一個用作名片主檔的試算表檔案。
   - 需指定 `Contacts` 工作表（若不存在則由系統建立並加上欄位表頭）。

### 4.2 資料存取方式

1. **讀取資料：**
   - App 透過 Google Sheets API 讀取 `Contacts` 工作表，載入名片列表。
   - 可依需求實作分頁或簡易快取，以避免一次載入過多資料造成效能問題。
2. **新增資料：**
   - App 在新增名片時，應：
     - 產生唯一 `id`。
     - 組合名片欄位資料。
     - 設定 `source = scan` 或 `manual`。
     - 填入 `created_at`、`updated_at` 為當前時間。
     - 透過 Google Sheets API 於 `Contacts` 中新增一列。
3. **更新資料：**
   - App 進行編輯時，需以 `id` 作為唯一鍵，定位對應列後更新其欄位。
   - 更新時必須同步更新 `updated_at` 欄位。
4. **刪除資料：**
   - 第一版可選擇：
     - 直接刪除該列，或
     - 提供「軟刪除」欄位（例如新增 `is_deleted` 欄位），實務上可視需求調整。

### 4.3 同步與一致性原則（簡化版）

- 以 Google 試算表為主資料來源，App 為「線上即時存取」模式。
- 操作原則：
  1. App 在編輯或刪除資料前，先取得指定 `id` 的最新資料。
  2. 操作完成後立即寫回試算表。
- 若發生極端情況（同一筆名片同時在手機與電腦上被修改）：
  - 以後送出的修改為準（last write wins），並由 `updated_at` 記錄最終時間點。
  - 本版本不實作複雜版本控制，必要時可在後續版本導入。

## 5. 名片掃描與影像管理需求

### 5.1 掃描流程（App 端）

1. 使用者於 App 中選擇「新增名片（掃描）」功能。
2. App 呼叫相機拍照，或從相簿選擇既有名片照片。
3. 影像送交 OCR / AI 服務處理（可為第三方 API 或內建模型）：
   - 解析姓名、公司、職稱、電話、Email、地址等欄位。
4. App 呈現「預填表單」畫面，讓使用者確認與修改欄位內容。
5. 使用者按下儲存後：
   - 影像上傳至 Google Drive 指定資料夾。
   - 取得該影像檔案的 URL，填入 `image_url` 欄位。
   - 透過 Google Sheets API 將名片資料寫入 `Contacts` 工作表。

### 5.2 影像檔案管理

- 可於 Google Drive 建立特定資料夾，例如：`BusinessCardImages`。
- 每張名片影像檔案命名建議包含：`id` 與建立日期，例如：`{id}_2025-11-21.jpg`。
- App 端只需保存 `image_url`，實際儲存與存取由 Google Drive 管理。

---

## 6. 安全性與權限需求

1. App 僅在使用者明確授權後，才能存取其 Google 試算表與 Drive 檔案。
2. 所有 API 呼叫需遵循 Google OAuth 安全性要求。
3. 建議在 App 端提供：
   - 啟動鎖（PIN 碼或生物辨識），避免手機遺失時個資外洩。
4. 使用者可在 Google 帳號安全性設定中隨時撤銷 App 的存取權限。

## 7. 未來擴充方向（預留說明）

本文件為「第一版」需求，聚焦於：

- 以 Google 試算表作為主資料庫。
- 支援手機端掃描、電腦端編輯與查詢。

未來可考慮的擴充包含：

1. **Web 後台管理介面：**
   - 建立專用管理後台（Web App），提供更友善的查詢、批次操作與報表功能。
   - 後端資料庫可改為 MySQL / PostgreSQL / Supabase 等，Google 試算表改為匯入／匯出介面。

2. **互動紀錄（簡易 CRM）：**
   - 另外建立 `Interactions` 工作表，紀錄每次會議、簡報或聯絡紀錄。
   - 列出近期未跟進的客戶清單。

3. **權限與多人協作：**
   - 未來若同一份名片資料需由多人共同維護，可規劃權限角色（只讀／可編輯）。
